# CS-320: Software Testing, Automation, and Quality Assurance

This repository contains my work from CS-320 at Southern New Hampshire University. It includes the Contact Service files from Project One and my Summary and Reflections Report from Project Two. Throughout this course, I worked with Java and JUnit 5 to develop and test software based on specific requirements. These projects helped me build a better understanding of how testing contributes to software reliability, security, and long-term maintainability.

## How can I ensure that my code, program, or software is functional and secure?

One of the biggest lessons I took away from this course was that just because a program runs successfully does not necessarily mean it is reliable or secure. Throughout Project One, I created JUnit tests that examined both expected behavior and situations where the program should reject certain inputs. For example, I tested whether the Contact Service would prevent duplicate IDs and whether the Appointment Service would reject dates in the past. Across all three services, I successfully passed 44 JUnit tests and achieved 88% combined instruction coverage. While I was happy with those results, I also learned that test coverage alone does not guarantee that every issue has been identified. With my background in security, I understand the importance of looking for potential weaknesses rather than assuming something is safe simply because it appears to work. Moving forward, I want to continue developing that mindset through automated testing, input validation, and reviewing my code for possible vulnerabilities.

## How do I interpret user needs and incorporate them into a program?

Before this course, I understood the importance of following project requirements, but working through these assignments helped me recognize how much detail goes into turning those requirements into functional software. Each of the three services had its own expectations regarding what information could be entered, modified, or removed. For example, the Contact Service required specific limitations on contact information, while the Task Service needed to support adding, updating, and deleting tasks. I approached these requirements by breaking them down into individual functions and then creating tests to determine whether the program behaved correctly. Something I learned throughout this process was that developers cannot rely entirely on how they expect users to interact with a program. They also need to consider mistakes, unexpected inputs, and situations that might not have been obvious during development. This experience reinforced the importance of understanding requirements from the user's perspective rather than focusing only on making the code work.

## How do I approach designing software?

When approaching software design, I prefer to start by understanding what needs to be accomplished and then breaking the project into smaller sections. Throughout this course, I found that keeping my classes and tests organized made it much easier to identify problems and understand where something might have gone wrong. Rather than creating complicated tests that examined several unrelated functions, I focused on testing individual requirements. For example, I separated the Task Service tests for adding, updating, and deleting tasks so failures could be identified more easily. I also used assertions such as assertEquals() and assertThrows() to verify results and confirm that invalid operations were handled appropriately. Another important lesson was recognizing how easily developers can overlook problems in their own code because they already know how it is supposed to function. As I continue working toward my computer science degree, I want to carry that experience into future projects by prioritizing clear requirements, maintainable code, and testing throughout the development process.
